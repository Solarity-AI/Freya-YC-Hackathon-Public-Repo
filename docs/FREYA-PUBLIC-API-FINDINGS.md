# Public Freya docs: findings (2026-10-10)

Sources: llms-full.txt, freya-openapi.json (production spec), notes/*.md. Kit docs win where they document something (written for this event, run against staging).

## Headline

1. [PUBLIC-DOC] The public docs have no workflow create, update, dry-run or publish route, and no node, transition or workflow-tool schema. /workflow* is GET-only, no path contains 'publish', and GET /workflow/{id} types result.workflow.workflow as {}. The kit (workflow-format.md, tools-and-code.md, api.md:50-115) stays the only source for the workflow format and the create-to-publish flow.
2. [PUBLIC-DOC] Chat has three things the kit lacks (llms-full.txt:487,495,503). First, POST /chat/message takes versionId and fromMessageId, and returns messageId, warning and endedByAgent. Second, POST /chat/fork clones a call up to an anchor message, including its workflowSnapshot, into a dormant call on another version, agent or workflow. Third, POST /chat/end fires 'webhook + post-conversation analysis + end-of-call tools' and is idempotent (alreadyEnded).
3. [PUBLIC-DOC] /chat/message has a full error set: 404 call not found; 409 'Call has no resume anchor (no prior assistant turn)'; 422 'customerVariables too large'; 502 no response; 503 'Agent service not configured'; 504 timed out. message (1-10000 chars) is required on every turn, including the first. [INFERRED] Each turn resumes the call from stored state; it is not a live session.
4. [PUBLIC-DOC] Freya has a platform unit-test feature that the kit never mentions (/unit-tests*, llms-full.txt:1356-1432). It is a single-turn test from a message snapshot whose messages can carry nodeId and workflowSnapshot. It checks an LLM-judged expectation plus up to 50 assertions: routing (node_entered/route_target), extraction (exists/equals/contains/regex/absent, minConfidence) and tool_call (args subset/exact, negate). run-all takes repeat 1-20, entityVersionId, mockToolResults (untyped) and assistant/judge LLM overrides. [INFERRED] It probably does not use the one-simulation slot; staging availability is [UNCERTAIN].
5. [PUBLIC-DOC] Simulation details the kit does not show (openapi POST /simulations): mode defaults to 'voice'. Other defaults and ranges: maxConcurrentCalls 1-1000 (default 1), maxCallDurationSeconds 60-3600 (default 240), maxRetries 0-10 (default 3), runsPerPersona 1-50. customerVariablesMap values must be strings. Also available: agentVersionId, start:false with POST /simulations/{id}/start, and tags. The status enum is draft|running|paused|completed, with NO 'failed'. Iterations are listed newest first (max 200) and carry agentVersionNumber, runAssistantLlms, inconclusiveRuns, errorRuns and analyzingRuns.
6. [PUBLIC-DOC] Personas have systemPrompt and evaluationPrompt (up to 100k chars each). They can be updated with PUT and deleted with DELETE (409 if in use, unless force=true). Batch create takes 1-200, and POST /personas/preview generates personas. K04's claim that 'personas only accumulate' is wrong.
7. [PUBLIC-DOC] GET /call/{id} REQUIRES the query parameter workspaceId, which freya.get_call (FP:79-81) does not send. The call record has about 50 fields, including entityVersionId and entityVersionNumber (which version ran), turnLatencyStats p50-p99, successCriteriaResult.relevantMessages, assertionResults, problems[] typed workflow/decision-llm/latency, insights, analysis, artifact, modality and originCallId. The public message item lacks nodeId, workflowSnapshot and system events. The kit observed them (api.md:314-334), and the unit-test input schema corroborates nodeId and workflowSnapshot.
8. [PUBLIC-DOC] Versions follow a working-copy model (llms-full.txt:1440). POST /versions/{type}/{id} validates a configSnapshot (422 if invalid) and applies it to the working copy. Branches work like pull requests: JSON-Patch or full-config commits, a conflict preview, and a 3-way merge. The only documented publish is POST /branches/{id}/rebase with publish:true. It is gated by unit-test and simulation 'checks' unless force:true. The version list pages at 50/100 and states NO order. /graph returns up to 1000 commits with per-version checks. [INFERRED] GET /workflow/{id} therefore returns the working copy.
9. [PUBLIC-DOC] The agent config is fully typed and is probably the same schema as a workflow's 'embedded agent config' (llms-full.txt:523-525). llmConfig provider and model are free strings, and experimental-5 appears nowhere. The config has separate routingLlmConfig and extractionLlmConfig. Other limits: maxTokens 1-4000, temperature 0-2, maximumDuration default 600 s. Tools: function.description is required, maxRetries is 0-5, and tools have preSpeech, maxPerNTurns and transition_to. Agent create and update can fail with 422 'The config selects a model that is outside its allowed hours'.
10. [PUBLIC-DOC] Rate limits are set per API key (rateLimit {requestsPerMinute, requestsPerDay}); the values are undocumented. GET /api-keys/check returns valid, workspaceId, expiresAt and rateLimit in one call. A 429 is declared only on /export and on invitations; no Retry-After or X-RateLimit headers are declared. The REST API 'is still experimental and the definitions may change without immediate notice' (llms-full.txt:767).
11. [PUBLIC-DOC] The public docs are thinner than the kit says ('documented in full', api.md:5). The Simulations and AI-Studio guide links are dead (llms-full.txt:3997,4001), and 142 of 156 api-reference pages are one-line stubs. The local OpenAPI is newer than the stubs: the merge-branch stub (llms-full.txt:316) omits the checks gate. The conceptual guides use an Agent/Function/Condition/Wait/Loop/Error-node and 'parallel flow' vocabulary that the kit's node_type enum does not have (llms-full.txt:4526-4560). Trust the kit there.
12. [PUBLIC-DOC] The knowledgebase is workspace-wide and 'available to all agents ... automatically. No per-agent configuration is needed' (llms-full.txt:3951). It has no public REST write route. [INFERRED] It does not travel with an exported workflow. [UNCERTAIN] Whether it injects a retrieval tool into workflow agents.

## Open questions answered or narrowed

- **K08 Q-05(e): What is the body of a later chat turn, and what does /chat/end return?** → Start a call with agentId or workflowId and no callId. Continue it with callId; message is required on every turn. /chat/end {callId} returns {callId, ended:true, endedReason, alreadyEnded?}. It is idempotent, and it fires the webhook, the async analysis and the end-of-call tools. Still open: whether customerVariables sent on later turns are merged. _[llms-full.txt:487, llms-full.txt:503; openapi POST /chat/message requestBody required ["message"]; openapi POST /chat/end responses.200 result {callId, ended, endedReason, alreadyEnded}; confidence high]_
- **K08 Q-05(c): Does get_call work on a chat callId?** → Chat calls are ordinary call records: GET /call/{id} has modality voice|text and channel whatsapp|api. But workspaceId is a REQUIRED query parameter on GET /call/{callId}, and freya.get_call does not send it. Call the route through freya.api with workspaceId. The public message schema lacks nodeId, workflowSnapshot and events; the kit observed them. _[openapi GET /call/{callId} parameters[workspaceId].required=true, result.call.modality; FP:79-81; api.md:314-334; confidence medium]_
- **K08 Q-05(a) / SD U14: Do chat turns run tools against the bank?** → In-call tools are not stated. /chat/end does fire 'end-of-call tools' for a chat call, and chat 'drives a Freya agent or workflow turn-by-turn' on the same pipecat runtime. So tools very likely run in chat. Keep the 2-minute U14 ledger check. _[llms-full.txt:487, llms-full.txt:503 [INFERRED]; confidence medium]_
- **SD E5(1) / K08 Q-01: Does an end_of_call lifecycle tool fire when a chat ends?** → Yes, when the chat is ended with POST /chat/end: it 'tells pipecat to fire the end-of-call lifecycle (webhook + post-conversation analysis + end-of-call tools)'. Still open: (2) whether it skips calls ended on e_end, (3) whether hooks run on lifecycle tools, (4) what an abandoned chat (no /chat/end) does, and the node-scope rule of TC:560. _[llms-full.txt:487; openapi POST /chat/end description; confidence medium]_
- **K08 Q-14 / SD E8: Who speaks first, and what does chat turn 1 look like?** → On the chat API a customer message is mandatory on turn 1, so the first response always answers a user message. For a plain agent, firstMessageMode defaults to assistant-waits-for-user. A call whose turn produced no assistant message cannot be resumed (409 'no resume anchor'). This supports keeping s_open as a tts conversation node. Who speaks first in simulations stays open. _[openapi POST /chat/message required [message], responses.409; openapi POST /agents body.config.llmConfig.firstMessageMode default assistant-waits-for-user; confidence medium]_
- **K08 Q-23: What simulation status values exist?** → draft, running, paused, completed. There is no 'failed' in the enum. draft occurs only with start:false and needs POST /simulations/{id}/start; that call returns 409 if the simulation is not a draft. Keep 'failed' as a harmless terminal state in polling, and never send start:false. _[openapi GET /simulations parameters[status].schema.enum; openapi POST /simulations/{simulationId}/start description and responses.409; confidence high]_
- **K08 Q-23: Is iterations[0] the correct, newest iteration? Where is agentVersionNumber?** → Yes. Iterations are 'newest first', limit default 100, max 200, with a total. agentVersionId, agentVersionNumber, agentLlm, runAssistantLlms and params sit on each iteration. The call record has entityVersionNumber, and GET /simulations/{id} returns publishedVersionId. _[openapi GET /simulations/{simulationId}/iterations description, result.iterations[]; openapi GET /call/{callId} result.call.entityVersionNumber; openapi GET /simulations/{simulationId} result.publishedVersionId; confidence high]_
- **K08 Q-23: What run outcome values exist beyond pass, fail, queued and running?** → Iterations count inconclusiveRuns, errorRuns and analyzingRuns as well as passed and failed runs. So inconclusive, error and analyzing outcomes exist, and verdicts may still be 'analyzing' after the simulation reports completed. Wait for analyzingRuns == 0 before reading verdicts. _[openapi GET /simulations/{simulationId}/iterations result.iterations[].inconclusiveRuns/errorRuns/analyzingRuns [INFERRED for the semantics]; confidence medium]_
- **K08 Q-23: What are the limits on maxConcurrentCalls, maxCallDurationSeconds, runsPerPersona and personas, and what are the mode values?** → maxConcurrentCalls 1-1000 (default 1); maxCallDurationSeconds 60-3600 (default 240); runsPerPersona 1-50 (default 1); maxRetries 0-10 (default 3); selectedPersonaIds 1-1000; tags at most 50. mode is voice|chat and DEFAULTS TO voice, so always send chat. customerVariablesMap values are strings only. _[openapi POST /simulations requestBody properties (minimum/maximum, mode.default='voice', customerVariablesMap additionalProperties string); openapi GET /simulations result.simulations[].settings defaults; confidence high]_
- **K08 Q-23 / O-6: Is there a persona limit or a delete route?** → PUT /personas/{id} and DELETE /personas/{id} exist; DELETE returns 409 while simulations use the persona, unless force=true. Create takes 1-200 personas per request. No total cap is documented. K04's 'personas only accumulate' is wrong. _[openapi PUT /personas/{personaId}, DELETE /personas/{personaId} (409, force); openapi POST /personas body.personas minItems 1 maxItems 200; confidence high]_
- **SD §15 K7 / K08 Q-23: Is there a cancel route for a stuck simulation?** → Narrowed, not answered. PUT /simulations/{id} accepts status draft|running|paused|completed, and DELETE /simulations/{id} 'deletes a simulation and all associated data'. Whether either stops dispatch is undocumented. Prefer one PUT {status:'paused'} after a timeout. Never DELETE, because that may remove the cited calls. _[openapi PUT /simulations/{simulationId} body.status; llms-full.txt:977; confidence low]_
- **K08 Q-23 / C-10: Which routes need workspaceId?** → A required query parameter on GET /call, GET /call/{id}, /personas (list), /simulations (list and tags), /workflow, /workflow/{id}, /versions/..., the unit-test lists, and /simulations/version-checks. It is taken from the token on POST /simulations, POST /personas, GET /simulations/{id}, /chat/* and /api-keys/check. It goes in the body on POST /versions and on unit-test create and run-all. _[openapi parameters of each operation (e.g. GET /personas parameters[workspaceId].required; POST /versions/{entityType}/{entityId} body.workspaceId); confidence high]_
- **K08 Q-23: What are the rate limits, and what is the 'concurrent simulations' error?** → Rate limits are per key: rateLimit {requestsPerMinute, requestsPerDay}. The calling key's values can be read with GET /api-keys/check, but the event values are unknown. No 429 is declared on chat, simulation, persona or workflow routes, and no Retry-After header is declared. The concurrent-simulation refusal is not in the spec (no 409 or 429 on create). Pre-check with GET /simulations?status=running. _[openapi GET /api-keys/check result.rateLimit; openapi POST /api-keys body.rateLimit; openapi POST /export responses.429 (only such route besides invitations); confidence high]_
- **K08 Q-08(e): Does GET workflow return the newest saved version or the published one?** → Workflows have a 'live working copy', and versions are snapshots applied to it. So GET /workflow/{id} very likely returns the working copy, not the published version. Our flow publishes the newest save, so the two coincide. Assert that published versionNumber == newest versionNumber before export. _[llms-full.txt:1440; openapi GET /workflow/{workflowId} result.workflow (agentId, updatedAt present) [INFERRED]; confidence medium]_
- **SD L3 / K08 Q-08(d): Is the version list ordered newest first?** → The public spec states no order and has no sort parameter; limit defaults to 50, max 100. The kit says 'newest version first' (api.md:106), and freya.update_workflow takes max(versionNumber) over the first page only. Use limit=100, assert total <= limit, and take max(versionNumber). Or use /graph (up to 1000 commits). _[openapi GET /versions/{entityType}/{entityId} parameters limit default 50 maximum 100; openapi GET /versions/{entityType}/{entityId}/graph; FP:61-62; confidence high]_
- **K08 Q-02 / T-15: What are the maxRetries and timeoutMs bounds?** → On agent tools, config.maxRetries is 0-5 and timeoutMs is >0, with no defaults. The schema is the agent-tool one; workflow tools presumably share it. What counts as 'failed' is still open. _[openapi POST /agents body.config.llmConfig.tools[].config.maxRetries (min 0 max 5), .timeoutMs (exclusiveMinimum 0); confidence medium]_
- **K08 Q-22: What is the endedReason vocabulary, e.g. at the 420 s limit?** → Generic values exist: customer-ended-call and assistant-ended-call (end-of-call report); exceeded-max-duration, inactivity-ended-call, voicemail and never_connected (campaign retry conditions). The duration cap probably yields exceeded-max-duration. An end_call node's endedReason stays the terminal function.name (kit). _[openapi POST /webhooks/end-of-call-report body.endedReason; openapi POST /campaign body.retryConditions enum; api.md:310; confidence medium]_
- **K08 Q-10 / O-3: What does the judge see?** → Narrowed only. The platform's judges can be fed engine events: simulation assertions have contextConfig {includeRoutingEvents, includeExtractionEvents, includeToolCalls, includeOtherEvents}, and unit tests have the same judgeContext. Personas have an evaluationPrompt, and successCriteriaResult carries relevantMessages and timeTaken. Whether the persona successCriteria judge sees events by default is not stated. _[openapi GET /simulations/{simulationId} result.assertions[].contextConfig; openapi POST /unit-tests body.judgeContext; openapi POST /personas body.personas[].evaluationPrompt; openapi GET /call/{callId} result.call.successCriteriaResult; confidence low]_
- **K08 Q-05(h,i) / O-1: Can a hidden-brief agent be tested past identity without practice customers?** → There is a new candidate path: unit-test run-all accepts mockToolResults (an untyped object), which might mock verify_identity and get_account. Its key and value shape are unknown, as is whether engine-run pre_actions are mockable. The fork path does not help here, because tools after the anchor still hit the real bank. _[openapi POST /unit-tests/run-all body.mockToolResults (additionalProperties {}); llms-full.txt:495; confidence low]_
- **K08 Q-08(b) / SD E0: What is the default model after create?** → Not answered for workflows. GET /agents/defaults returns the platform default agent config used by the editor's reset controls. FP:55-56 says a non-event model means 'a chat turn ... cannot start', which matches the public 503 'Agent service not configured' [INFERRED]. Models can be time-gated: agent create and update return 422 'outside its allowed hours'. _[openapi GET /agents/defaults description; openapi POST /agents responses.422; FP:55-56; confidence low]_
- **K08 Q-08(k) / O-7: Should the export carry agent_config?** → Still an organiser question. The public docs confirm that a workflow has an 'embedded agent config', and that a UI-style save to it creates a new version (/custom/abbreviations). So agent_config is a real, versioned part of a workflow. _[llms-full.txt:523-525; confidence low]_
- **SD E4: How can extraction quality be calibrated without spending simulation slots?** → Unit tests make it measurable, if the route works on staging. Use extraction assertions with minConfidence 0-1, repeat 1-20, assistantLlmOverride=experimental-5, and up to 200 tests per run-all. Alternatively, fork one pre-write negotiation checkpoint many times through /chat/fork. _[openapi POST /unit-tests body.assertions[] (extraction), POST /unit-tests/run-all body.repeat/unitTestIds/assistantLlmOverride; llms-full.txt:495; confidence medium]_
- **SD E6: How can per-turn latency be measured?** → call.turnLatencyStats {p50,p75,p90,p95,p99,avg,count} (units not stated) and unit-test run latencyMs. No code-snippet size limit is documented. _[openapi GET /call/{callId} result.call.turnLatencyStats; openapi GET /unit-tests/runs/{runId} result.latencyMs; confidence low]_
